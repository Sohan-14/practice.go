**P12 — TLS/HTTPS**

Here's why this is the critical next step:

**Without TLS, everything else is vulnerable.**

All the security work we've done — input validation, rate limiting, structured logging — happens over plaintext HTTP. That means:

- API keys and auth tokens are visible to anyone on the network
- User data (passwords, emails, personal info) can be intercepted
- Rate limiting can be bypassed by someone modifying requests in transit
- Man-in-the-middle attacks can inject malicious responses

TLS encrypts the entire connection, making all of this impossible. It's the foundation of secure communication.

### **The Roadmap for P12**

| Module | What you'll learn |
| --- | --- |
| **Reproduce the problem** | See what plaintext HTTP looks like on the wire |
| **Generate certificates** | Create self-signed certs for development |
| **Enable TLS** | Switch from `ListenAndServe` to `ListenAndServeTLS` |
| **TLS configuration** | Harden the TLS settings (cipher suites, versions) |
| **HTTP to HTTPS redirect** | Handle clients that still use HTTP |
| **Polish** | Certificate management, Let's Encrypt, production considerations |

# **Module 1: Reproduce the Problem**

**Goal:** Observe what plaintext HTTP looks like on the network, proving that everything is visible to anyone who can intercept the traffic.

### Step 1: Start your server

```go
go run main.go
```

Your server is running on `http://localhost:8080` (plaintext HTTP).

**Step 2: Make a request with sensitive data**

Send a request that includes "sensitive" information (in a real app, this would be passwords, API keys, user data):

```go
curl -X POST http://localhost:8080/api/users \
  -H "Content-Type: application/json" \
  -d '{"name":"Alice","email":"alice@example.com","password":"SuperSecret123!"}'
```

**Step 3: Intercept the traffic**

We'll use `tcpdump` or `tshark` to capture the network traffic. Open a new terminal and run:

**Option A: Using tcpdump (macOS/Linux)**

```go
sudo tcpdump -i lo0 -A -s 0 'tcp port 8080'
```

**Option B: Using tshark (if you have Wireshark installed)**

```go
sudo tshark -i lo0 -Y "tcp.port==8080" -T fields -e data
```

**Option C: Using curl with verbose output (simpler, less realistic)**

If you don't have tcpdump/tshark, you can at least see what the client sends:

```go
curl -v -X POST http://localhost:8080/api/users \
  -H "Content-Type: application/json" \
  -d '{"name":"Alice","email":"alice@example.com","password":"SuperSecret123!"}'
```

**Step 4: Observe the result**

**Everything is visible:**

- The URL path (`/api/users`)
- The headers (including `Content-Type`)
- The entire request body, including the password `SuperSecret123!`

### Step 5: The danger

This is what happens on an untrusted network (public WiFi, corporate network, internet):

- Anyone with packet capture tools can read your traffic
- Passwords, API keys, session tokens — all exposed
- An attacker can modify requests in transit (change the email, inject malicious data)
- They can also modify responses (inject fake data, redirect to malicious sites)

This is why **every production API must use HTTPS**.

### Step 6: What HTTPS looks like

We'll implement this in the next modules, but here's a preview. With HTTPS, the same request would look like this on the wire:

```
Client Hello (TLS handshake)
...
[Encrypted application data]
...
```

The actual HTTP request and response are encrypted inside the TLS tunnel. An eavesdropper sees only encrypted bytes — they can't read the URL, headers, or body.

# **Module 2: Generate TLS Certificates**

To enable HTTPS, your server needs two things:

1. A **Private Key**: A secret cryptographic key that only your server knows. It's used to decrypt incoming traffic and sign outgoing traffic.
2. A **Public Certificate**: A file that contains your server's public key and identity information. It is given to clients so they can encrypt data *for* your server.

In production, a trusted third party (a Certificate Authority, like Let's Encrypt) signs your certificate to prove you are who you say you are.

For local development, we use a **self-signed certificate**. It provides the exact same encryption, but because it's not signed by a trusted authority, web browsers will show a warning. Command-line tools like `curl` can easily bypass this warning for testing.

### Step 1: Generate the certificates

We will use `openssl`, the industry-standard tool for this. Open your terminal in your project directory and run:

```go
openssl req -x509 -newkey rsa:4096 -keyout key.pem -out cert.pem -days 365 -nodes -subj "/CN=localhost"
```

**What this command does (line-by-line)**

`req`

Certificate request and cert generating utility.

-x509

Output a self-signed certificate instead of a certificate request.

`-newkey rsa:4096`

Generate a new RSA private key that is 4096 bits long (very secure).

`-keyout key.pem`

Save the private key to a file named `key.pem`.

`-out cert.pem`

Save the public certificate to a file named `cert.pem`.

`-days 365`

Make the certificate valid for 1 year.

`-nodes`

**No DES**. Do not encrypt the private key file with a password. (Crucial for automated servers, otherwise the server would prompt for a password on every restart).

`-subj "/CN=localhost"`

Set the Common Name (CN) to `localhost`. This tells the client "this cert is for localhost".

**Step 2: Verify the files**

```go
ls -l *.pem
```

You should see two files:

- `cert.pem` (The public certificate, safe to share)
- `key.pem` (The private key, **must be kept secret**)

**Step 3: Peek inside the certificate (Optional but educational)**

You can read the public certificate to see what's inside it:

```go
openssl x509 -in cert.pem -text -noout
```

Look for these lines in the output:

```go
Subject: CN = localhost
Validity
    Not Before: Nov  4 12:00:00 2026 GMT
    Not After : Nov  4 12:00:00 2027 GMT
```

This proves the certificate claims to be for `localhost` and is valid for 1 year.

### Crucial Security Rule

**Never commit `key.pem` to Git.**
If your private key is exposed, anyone can impersonate your server or decrypt past traffic (if they recorded it). In a real project, you would add `*.pem` or specifically `key.pem` to your `.gitignore` file, and inject it securely via environment variables or a secrets manager in production.

# **Module 3: Enable TLS in Go**

Now we flip the switch. We are going to change exactly **one line of code** to transform your server from plaintext HTTP to encrypted HTTPS.

### Step 1: Update `main.go`

Find this line in your `main()` function (inside the goroutine that starts the server):

```go
if err := server.ListenAndServe(); err != nil && err != http.ErrServerClosed {
```

Change it to use `ListenAndServeTLS`, passing the paths to your certificate and key:

```go
if err := server.ListenAndServeTLS("cert.pem", "key.pem"); err != nil && err != http.ErrServerClosed {
```

That’s it. Go’s standard library handles the entire TLS handshake, encryption, and decryption automatically.

**Step 2: Run the server**

```go
go run main.go
```

You should see your normal startup log:

```go
server starting on :8080
```

*(Note: It's still port 8080, but now it expects TLS connections instead of plaintext).*

**Step 3: Test with plaintext HTTP (The Failure)**

Try to hit the server with normal HTTP:

```go
curl http://localhost:8080/health
```

```go
curl: (52) Empty reply from server
```

*(Or a similar connection error).*

**Why?** Your `curl` client is sending plaintext HTTP. The server is expecting a TLS handshake. They are speaking different languages, so the connection drops. This proves the server is no longer accepting plaintext traffic.

**Step 4: Test with HTTPS (The Success)**

Now, tell `curl` to use HTTPS. Because we generated a **self-signed** certificate, `curl` will normally reject it (saying the certificate is not trusted by a known authority). We use the `-k` (or `--insecure`) flag to tell `curl` to skip that verification for testing purposes:

```go
curl -k https://localhost:8080/health
```

```go
{"status":"ok"}
```

# **Module 4: TLS Configuration — Hardening for Production**

Go's default TLS settings are actually quite good. But in enterprise environments, security policies often require **explicit hardening**:

- Forcing a minimum TLS version (e.g., TLS 1.2 or 1.3 only)
- Disabling weak cipher suites
- Meeting compliance standards (PCI-DSS, HIPAA, SOC 2)

### Step 1: Create a custom `tls.Config`

Update your `main.go` to configure the server's TLS settings explicitly:

```go
TLSConfig: &tls.Config{
			// Force TLS 1.2 or higher (disable TLS 1.0 and 1.1)
			MinVersion: tls.VersionTLS12,

			// Use only strong cipher suites
			CipherSuites: []uint16{
				tls.TLS_ECDHE_ECDSA_WITH_AES_256_GCM_SHA384,
				tls.TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384,
				tls.TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256,
				tls.TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256,
				tls.TLS_ECDHE_ECDSA_WITH_CHACHA20_POLY1305,
				tls.TLS_ECDHE_RSA_WITH_CHACHA20_POLY1305,
			},

			// Prefer server's cipher order (not client's)
			PreferServerCipherSuites: true,
		},
```

`MinVersion: tls.VersionTLS12`

Rejects TLS 1.0 and 1.1 (both have known vulnerabilities). TLS 1.2 is the minimum for modern security.

CipherSuites

Explicitly lists only strong encryption algorithms. Removes weak ones like RC4, 3DES, etc.

`PreferServerCipherSuites: true`

Your server chooses the cipher, not the client. Prevents downgrade attacks.

# **Module 5: HTTP to HTTPS Redirect**

Right now, if a user types `http://localhost:8080` in their browser, they get a connection error. That's bad user experience. In production, you want to **automatically redirect** all HTTP traffic to HTTPS.

### The Pattern

Run **two servers**:

1. **Port 80** (HTTP) — accepts plaintext, immediately redirects to HTTPS
2. **Port 8080** (HTTPS) — your actual TLS server

When a client hits `http://...`, the port 80 server responds with:

HTTP/1.1 301 Moved Permanently
Location: https://localhost:8080/health

The browser automatically follows the redirect to HTTPS.

**Step 1: Create the redirect handler**

Add this function to your `main.go`:

```go
// redirectHandler redirects all HTTP requests to HTTPS.
func redirectHandler(w http.ResponseWriter, r *http.Request) {
	// Build the HTTPS URL
	httpsURL := "https://" + r.Host + r.URL.RequestURI()

	// 301 = permanent redirect (browsers cache this)
	// 302 = temporary redirect (browsers don't cache)
	http.Redirect(w, r, httpsURL, http.StatusMovedPermanently)
}
```

### What this does

- `r.Host` — the hostname the client requested (e.g., `localhost:8080`)
- `r.URL.RequestURI()` — the full path + query string (e.g., `/health?name=Alice`)
- `http.Redirect` — sets the `Location` header and status code automatically

**Step 2: Run both servers concurrently**

```go
func main() {
	logger = slog.New(slog.NewJSONHandler(os.Stdout, nil))

	// ... your existing middleware setup ...

	// HTTPS server (your main server)
	httpsServer := &http.Server{
		Addr:         ":8080",
		Handler:      handler,
		ReadTimeout:  5 * time.Second,
		WriteTimeout: 10 * time.Second,
		TLSConfig: &tls.Config{
			MinVersion: tls.VersionTLS12,
			// ... your cipher suites ...
		},
	}

	// NEW: HTTP redirect server
	httpRedirectMux := http.NewServeMux()
	httpRedirectMux.HandleFunc("/", redirectHandler)

	httpServer := &http.Server{
		Addr:    ":80",
		Handler: httpRedirectMux,
	}

	// Channel for server errors
	serverErr := make(chan error, 2) // buffered for 2 servers

	// Start HTTP redirect server
	go func() {
		log.Println("HTTP redirect server starting on :80")
		if err := httpServer.ListenAndServe(); err != nil && err != http.ErrServerClosed {
			serverErr <- err
		}
	}()

	// Start HTTPS server
	go func() {
		log.Println("HTTPS server starting on :8080")
		if err := httpsServer.ListenAndServeTLS("cert.pem", "key.pem"); err != nil && err != http.ErrServerClosed {
			serverErr <- err
		}
	}()

	// Wait for shutdown signal or startup error
	sigChan := make(chan os.Signal, 1)
	signal.Notify(sigChan, syscall.SIGINT, syscall.SIGTERM)

	select {
	case err := <-serverErr:
		log.Fatalf("server failed: %v", err)
	case sig := <-sigChan:
		log.Printf("received signal %v, shutting down", sig)
	}

	// Graceful shutdown for both servers
	ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()

	// Shutdown both servers
	if err := httpServer.Shutdown(ctx); err != nil {
		log.Printf("HTTP server forced shutdown: %v", err)
	}
	if err := httpsServer.Shutdown(ctx); err != nil {
		log.Printf("HTTPS server forced shutdown: %v", err)
	}

	log.Println("graceful shutdown complete")
}
```

### Key changes

1. **Two servers**: `httpServer` on port 80, `httpsServer` on port 8080
2. **Two goroutines**: Each server runs in its own goroutine
3. **Buffered error channel**: `make(chan error, 2)` to handle errors from both servers
4. **Graceful shutdown for both**: We call `Shutdown` on both servers

# **Module 6: Polish — Production Certificates with Let's Encrypt**

Self-signed certificates are perfect for learning and local development. But in production, they are a disaster: users see scary browser warnings, API clients reject the connections, and you have to manually regenerate and distribute them every year.

The industry standard solution is **Let's Encrypt**: a free, automated, and open Certificate Authority (CA).

### The Concept: ACME Protocol

Let's Encrypt uses the **ACME** (Automated Certificate Management Environment) protocol. Instead of you manually generating a CSR and emailing it to a CA, your server talks directly to Let's Encrypt to prove it owns the domain and get a trusted certificate automatically.

**The Flow:**

1. Your server starts and listens on port 80 (HTTP) and 443 (HTTPS).
2. A user visits `https://yourdomain.com`.
3. Your Go server realizes it doesn't have a certificate for `yourdomain.com` yet.
4. It pauses the connection and contacts Let's Encrypt: *"I need a cert for yourdomain.com"*.
5. Let's Encrypt says: *"Prove you control this domain by serving this specific random string at `http://yourdomain.com/.well-known/acme-challenge/xyz`"*.
6. Your Go server automatically serves that string on port 80.
7. Let's Encrypt verifies it, issues the certificate, and your Go server caches it and serves it to the user over port 443.
8. **Bonus:** Go automatically renews the certificate in the background before it expires (Let's Encrypt certs last 90 days).

### The Go Tool: `autocert`

Go provides a built-in package for this: `golang.org/x/crypto/acme/autocert`.

### Step 1: The Code

Here is how you replace your manual `cert.pem` and `key.pem` with zero-touch automation.

First, get the package:

```go
go get golang.org/x/crypto/acme/autocert
```

Then, update your server setup in `main.go`:

```go
import (
	// ... your existing imports
	"golang.org/x/crypto/acme/autocert"
)

func main() {
	// ... your existing middleware and handler setup ...

	// 1. Create the autocert manager
	certManager := autocert.Manager{
		Prompt:     autocert.AcceptTOS, // Automatically accept Let's Encrypt Terms of Service
		HostPolicy: autocert.HostWhitelist("yourdomain.com", "www.yourdomain.com"), // Only allow these domains
		Cache:      autocert.DirCache("certs"), // Save certs to a local "certs" directory so we don't request them on every restart
	}

	// 2. Configure the HTTPS server
	httpsServer := &http.Server{
		Addr:         ":443", // Standard HTTPS port
		Handler:      handler,
		ReadTimeout:  5 * time.Second,
		WriteTimeout: 10 * time.Second,
		TLSConfig: &tls.Config{
			MinVersion: tls.VersionTLS12,
			// autocert provides a helper to get the recommended TLS config
			GetCertificate: certManager.GetCertificate,
		},
	}

	// 3. Configure the HTTP server (for ACME challenges AND redirects)
	httpServer := &http.Server{
		Addr:    ":80", // Standard HTTP port
		Handler: certManager.HTTPHandler(nil), // nil means it will just handle ACME challenges.
		// Note: If you also want HTTP->HTTPS redirects, you'd wrap a custom mux with certManager.HTTPHandler(yourRedirectMux)
	}

	// ... start both servers in goroutines and handle graceful shutdown as before ...
}
```
