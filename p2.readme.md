P10 — No panic recovery

- **It finishes the availability theme.** Graceful shutdown protects requests when we *stop*. Panic recovery protects the service when a request *misbehaves*. Together: "one bad request can't hurt anyone else."
- **It's the best vehicle to learn middleware.** This is the real reason. Panic recovery is implemented as **middleware** — and middleware is the pattern behind almost every remaining problem on the sheet: logging (P6), rate limiting (P14), auth (P15), security headers (P16), request IDs. Learn it once here, reuse it everywhere.
- **It's small and satisfying.**

So we're not just fixing one bug — we're unlocking a pattern you'll use repeatedly.

# **Module 1: Reproduce the Problem**

**Goal:** add an endpoint that always panics, and observe — empirically — what happens to both the **client** and the **server**.

### Step 1 — Add a `/panic` endpoint

In your clean `main.go`, add the route with the others:

```go
mux.HandleFunc("GET /panic", panicHandler)
```

And add the handler:

```go
func panicHandler(w http.ResponseWriter, r *http.Request) {
	panic("something went terribly wrong")
}
```

**Step 2 — Run and hit it**

Terminal A:

```go
go run main.go
```

Terminal B:

```go
curl http://localhost:8080/panic
```

**Step 3 — Observe BOTH sides**

**What does curl show?** You should see a **broken** result — something like:

```go
curl: (52) Empty reply from server
```

or a connection reset. **Not** a clean error message, **not** a proper 500 response. Just a dropped connection.

**What does the server log show?** An uncontrolled panic — something like:

```go
http: panic serving 127.0.0.1:xxxxx: something went terribly wrong
goroutine 18 [running]:
main.panicHandler(...)
    ...stack trace...
```

**Step 4 — The important test: is the server still alive?**

Right after, still in Terminal B:

```go
curl http://localhost:8080/health
```

Observe the result. Two possibilities, and **both are problems**:

- If `/health` **works** → the server survived, but the panic client got a broken connection and *we had zero control* over the response or the log.
- If `/health` **fails** → one request took down the whole server for everyone.

### The lesson

An unhandled panic means:

- the client gets **nothing useful** (a dropped connection, not a clean error), and
- we have **no control** — no proper status code, no structured log, no graceful handling.

In production that's unacceptable. What we *want* is: **catch the panic, return a clean `500`, log it properly, keep serving everyone else.**

# **Module 2: `panic` and `recover` — the mechanics**

**panic vs. errors — when is each used**

Go has two ways to signal "something went wrong":

| Mechanism | Use for | How it behaves |
| --- | --- | --- |
| Returned `error` | **Expected** problems (bad input, file missing….) | A normal value you check with `if err != nil` |
| panic | **Unexpected/fatal** things (programmer bugs, broken invariants…) | Stops normal execution, unwinds the stack, crashes the program unless caught |

Rule of thumb: use `error` for anything you anticipate. Reserve `panic` for things that "can't happen." But — and this is the key point for a server — **even if a handler panics due to a bug, the whole service must not die.** So we catch it at the boundary and turn it into a clean error response.

**What happens when a panic fires**

1. Normal execution **stops immediately**.
2. The runtime starts **unwinding the stack** of the current goroutine.
3. As it unwinds, it runs all **deferred functions**.
4. If a deferred function calls **`recover()`**, the panic is caught and the crash stops.
5. If nothing recovers it, the panic reaches the top → the program crashes.

That step 3–4 is why **`recover()` only works inside a `defer`** — deferred code is the only code that runs during the unwind, so it's the only place with a chance to catch the panic.

**The pattern**

```go
defer func() {
	if r := recover(); r != nil {
		// handle the panic here
	}
}()
```

`recover()` returns the panic value if a panic is in flight, or `nil` if there isn't one.

So we check `if r := recover(); r != nil`.

### Two rules to remember

1. **`recover()` only works inside a `defer`.** Called anywhere else, it just returns `nil`.
2. **`recover()` only catches panics in the same goroutine.** This matters for us: each HTTP request runs in its own goroutine, so the `recover` must live in the same goroutine as the handler. Keep that in mind — it shapes how we build the middleware next.

# **Module 3: Middleware — the "wrap a handler" pattern**

This is the big one. Everything from here on (recovery, logging, auth, rate limiting) uses this exact pattern, so it's worth making it click properly.

**The foundation: a handler is just an interface**

In Go's `net/http`, everything hinges on one tiny interface:

```go
type Handler interface {
	ServeHTTP(ResponseWriter, *Request)
}
```

Anything that has a `ServeHTTP` method is a handler. That includes your functions, and — importantly — **`http.ServeMux` itself** (that's why you can pass `mux` to `server.Handler`).

### The key insight: handlers are values

Because a handler is just a value, you can:

- pass it around,
- and **wrap it with another handler**.

That's all middleware is: **a function that takes a handler and returns a new handler that adds behavior around it.**

The universal signature:

```go
func middleware(next http.Handler) http.Handler
```

### The adapter: `http.HandlerFunc`

To return "a handler" from our middleware, we use `http.HandlerFunc`. It's an adapter that turns a plain `func(w, r)` into something that satisfies the `http.Handler` interface. You'll see it in every middleware you ever write.

### Let's build one — a minimal request logger

This is a teaching vehicle (proper structured logging is later, as P6). Add this function to your `main.go`:

```go
// requestLogger wraps a handler and logs before and after it runs.
func requestLogger(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		// BEFORE the wrapped handler runs
		log.Printf("--> %s %s", r.Method, r.URL.Path)

		// call the next handler in the chain
		next.ServeHTTP(w, r)

		// AFTER the wrapped handler runs
		log.Printf("<-- done %s %s", r.Method, r.URL.Path)
	})
}
```

Now wrap your `mux` in `main()`. Change the server setup so it uses the wrapped version:

```go
	// Wrap the entire mux with the logger
	handler := requestLogger(mux)

	server := &http.Server{
		Addr:         ":8080",
		Handler:      handler, // use the wrapped mux, not the raw mux
		ReadTimeout:  5 * time.Second,
		WriteTimeout: 10 * time.Second,
	}
```

Server output:

```go
--> GET /health
<-- done GET /health
```

The request passed **through** the logger on its way in and out. That's middleware working.

**The mental model: layers**

```go
Request
   |
   v
requestLogger  (BEFORE)
   |
   v
mux            (routes to the right handler)
   |
   v
healthHandler  (does the real work)
   |
   v
requestLogger  (AFTER)
   |
   v
Response
```

Because we wrapped the whole `mux`, **every** request goes through the logger — without touching any individual handler. That's the power: add behavior to all handlers in one place.

**Bonus observation — hit `/panic`**

```go
curl http://localhost:8080/panic
```

Look at the server logs. You'll see:

```go
--> GET /panic
http: panic serving ...: something went terribly wrong
```

Notice: the `-->` line printed, but the `<-- done` line **did not**. The panic fired inside `next.ServeHTTP(...)` and blew straight past the "after" code. That's the exact gap our recovery will fill.

# **Module 4: Build the recovery middleware**

Now we combine the two pieces: the **catch mechanism** (Module 2) and the **wrapper shape** (Module 3).

**Answering the preview question: where does the `defer` go?**

It must be registered **before** we call `next.ServeHTTP(...)`. Here's why:

- A `defer` runs when the surrounding function exits — *including when it exits via a panic*.
- So we **register the safety net first**, then call the next handler.
- If the next handler panics, the panic unwinds through our closure, hits the `defer`, and `recover()` catches it.

If we put the `defer` *after* `next.ServeHTTP(...)`, it would never get registered — the panic would fire before we reached that line. **Placement is everything.**

**The middleware**

Add this to your `main.go`:

```go
// recoverMiddleware catches panics from downstream handlers and turns them
// into a 500 response, so one bad request can't break the connection or
// take down the server.
func recoverMiddleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		// Register the safety net BEFORE the risky call
		defer func() {
			if rec := recover(); rec != nil {
				log.Printf("recovered from panic: %v", rec)
				http.Error(w, "Internal Server Error", http.StatusInternalServerError)
			}
		}()

		// The risky call. If this panics, the defer above catches it.
		next.ServeHTTP(w, r)
	})
}
```

**A naming gotcha worth noting**

The handler receives `r *http.Request`. Inside the `defer`, if we wrote `if r := recover()`, that new `r` would **shadow** the request `r`. It compiles, but it's confusing and a common source of bugs. I used `rec` for the recovered value to keep them distinct. Remember this — you'll see it in real codebases.

### Apply it — and mind the order

You already have the logger. Now compose both, with the recovery as the **outermost** layer:

```go
	handler := recoverMiddleware(requestLogger(mux))
```

Why outermost? The recovery net should catch panics from **everything inside it** — the handlers *and* any other middleware. Reading the line inside-out: `mux` is wrapped by `requestLogger`, and that result is wrapped by `recoverMiddleware`.

Request flow:

```go
Request
  -> recoverMiddleware (defer registered)
     -> requestLogger  ("-->")
        -> mux -> your handler
     <- requestLogger  ("<--")
  <- recoverMiddleware
Response
```

**Run it — the moment of truth**

```go
go run main.go
```

```go
curl -i http://localhost:8080/panic
```

The `-i` flag shows the status line and headers. You should now see:

```go
HTTP/1.1 500 Internal Server Error
Content-Type: text/plain; charset=utf-8
...

Internal Server Error
```

That's a **clean 500 response** — not `socket hang up`, not an empty reply. The panic was caught and converted into a proper HTTP error.

Then confirm the server is still alive:

```go
curl http://localhost:8080/health
```

```go
{"status":"ok"}
```

# **Module 5: Verify thoroughly**

One clean `500` is a good smoke test, but a single pass isn't proof. Production engineering means verifying under the conditions that actually matter. Let's run a proper verification suite.

A handy tool first — print **only** the status code:

```go
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8080/health
```

- `s` → silent
- `o /dev/null` → throw away the body
- `w "%{http_code}\n"` → print just the status code

It prints `200`. We'll use this to check codes cleanly.

**Test 1 — The status code is exactly 500**

```go
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8080/panic
```

Expected: `500`.

Not `000` (broken connection), not `200`. Exactly `500`. This is the contract we're verifying.

**Test 2 — Repeated panics: the server stays stable**

Hammer `/panic` five times, then check health:

```go
for i in 1 2 3 4 5; do
  curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8080/panic
done

curl http://localhost:8080/health
```

Expected:

```go

500
500
500
500
{"status":"ok"}
```

# **Module 6: Polish — clean JSON errors and real debugging info**

It works, but two things are still amateur-grade:

1. The client gets plain text: `Internal Server Error`. Real APIs return **JSON** so clients can parse errors.
2. We log only the panic *message*. We don't log **where** it happened — which makes it useless for actually fixing the bug.

Let's fix both.

**Upgrade 1: capture the stack trace with `debug.Stack()`**

The `runtime/debug` package gives us `debug.Stack()`, which returns the current goroutine's **stack trace** — the chain of calls leading to the panic, with file names and line numbers.

Called inside the `recover` (during the unwind), it captures exactly where the panic occurred. That's what lets you actually find and fix the bug.

Upgrade 2: separate what the *logs* get from what the *client* gets

This is an important production principle:

- **Logs** get the full detail — panic value + stack trace — so *you* can debug.
- **The client** gets a clean, generic JSON error — nothing more.

Why not send the stack trace to the client? Because it leaks internal details — file paths, function names, line numbers, package structure. That's information an attacker can use and a client can't. **Diagnose server-side; apologize client-side.**

**The polished middleware**

Replace your `recoverMiddleware` with this, and reuse your existing `writeJSON` helper:

```go
func recoverMiddleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		defer func() {
			if rec := recover(); rec != nil {
				// Full detail goes to the server logs for debugging.
				log.Printf("recovered from panic: %v\n%s", rec, debug.Stack())

				// The client gets a clean, machine-readable error only.
				writeJSON(w, http.StatusInternalServerError, map[string]string{
					"error": "Internal Server Error",
				})
			}
		}()

		next.ServeHTTP(w, r)
	})
}
```

**Run it and observe both sides**

```go
go run main.go
```

**The client** now gets JSON:

```go
curl -i http://localhost:8080/panic
```

```go
HTTP/1.1 500 Internal Server Error
Content-Type: application/json

{"error":"Internal Server Error"}
```

Clean, parseable, no internal details.

**The server logs** now get the full story:

```go
recovered from panic: something went terribly wrong
goroutine 18 [running]:
runtime/debug.Stack()
    .../runtime/debug/stack.go:24
main.recoverMiddleware.func1()
    .../main.go:XX
main.panicHandler(...)
    .../main.go:XX
net/http.(*ServeMux).ServeHTTP(...)
    ...
```

Restructured main.go

```go
package main

import (
	"context"
	"encoding/json"
	"fmt"
	"log"
	"net/http"
	"os"
	"os/signal"
	"runtime/debug"
	"syscall"
	"time"
)

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /{$}", homeHandler)
	mux.HandleFunc("GET /health", healthHandler)
	mux.HandleFunc("GET /api/hello", helloHandler)
	mux.HandleFunc("GET /panic", panicHandler)

	handler := recoverMiddleware(requestLogger(mux))

	server := &http.Server{
		Addr:         ":8080",
		Handler:      handler,
		ReadTimeout:  5 * time.Second,
		WriteTimeout: 10 * time.Second,
	}

	// serverErr carries fatal startup errors (e.g. port already in use)
	// from the server goroutine back to main.
	serverErr := make(chan error, 1)

	go func() {
		log.Println("server starting on :8080")
		// http.ErrServerClosed is the expected result of a graceful Shutdown,
		// so we only report real errors.
		if err := server.ListenAndServe(); err != nil && err != http.ErrServerClosed {
			serverErr <- err
		}
	}()

	// Wait for either a shutdown signal or a startup failure.
	sigChan := make(chan os.Signal, 1)
	signal.Notify(sigChan, syscall.SIGINT, syscall.SIGTERM)

	select {
	case err := <-serverErr:
		log.Fatalf("server failed to start: %v", err)
	case sig := <-sigChan:
		log.Printf("received signal %v, shutting down", sig)
	}

	// Graceful drain, capped at 10 seconds.
	ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()

	if err := server.Shutdown(ctx); err != nil {
		log.Printf("forced shutdown: %v", err)
		os.Exit(1)
	}

	log.Println("graceful shutdown complete")
}

func panicHandler(w http.ResponseWriter, r *http.Request) {
	panic("something went terribly wrong")
}

func homeHandler(w http.ResponseWriter, r *http.Request) {
	fmt.Fprintln(w, "Welcome to my Go HTTP server!")
	fmt.Fprintln(w, "Try: /health or /api/hello?name=World")
}

func healthHandler(w http.ResponseWriter, r *http.Request) {
	writeJSON(w, http.StatusOK, map[string]string{"status": "ok"})
}

func helloHandler(w http.ResponseWriter, r *http.Request) {
	name := r.URL.Query().Get("name")
	if name == "" {
		name = "World"
	}
	writeJSON(w, http.StatusOK, map[string]string{
		"message": fmt.Sprintf("Hello, %s!", name),
	})
}

func writeJSON(w http.ResponseWriter, status int, data any) {
	w.Header().Set("Content-Type", "application/json")
	w.WriteHeader(status)
	json.NewEncoder(w).Encode(data)
}

// requestLogger wraps a handler and logs before and after it runs.
func requestLogger(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		// BEFORE the wrapped handler runs
		log.Printf("--> %s %s", r.Method, r.URL.Path)

		// call the next handler in the chain
		next.ServeHTTP(w, r)

		// AFTER the wrapped handler runs
		log.Printf("<-- done %s %s", r.Method, r.URL.Path)
	})
}

func recoverMiddleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		defer func() {
			if rec := recover(); rec != nil {
				log.Printf("recovered from panic: %v\n%s", rec, debug.Stack())

				writeJSON(w, http.StatusInternalServerError, map[string]string{
					"error": "Internal Server Error",
				})
			}
		}()

		next.ServeHTTP(w, r)
	})
}
```
